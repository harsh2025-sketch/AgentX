# AX-260–265 / AX-296–297 completion contract

This campaign slice completes request-sensitive filesystem structural governance, five bounded structural filesystem capabilities, and independent clipboard/keyboard verification adapters without creating a second authority path.

## Structural operations

`agentx.capabilities.filesystem_structural` provides create-directory, move-file, rename-file, delete-file and delete-empty-directory operations. Paths are explicit normalized absolute host paths. Move/rename are bounded regular-file operations with no replacement; rename is same-parent only. Directory deletion uses non-recursive `rmdir` semantics and rejects non-empty targets. No `safe` parameter, recursive-delete option, shell path, globbing or arbitrary command execution exists.

AX-260 request-sensitive risk is re-evaluated immediately before mutation from typed preflight facts. Filenames and other untrusted strings cannot lower the fixed capability governance ceiling or grant permission. Create/move/rename use `WRITE`; file/directory deletion retain explicit `DESTRUCTIVE` authority and destructive risk.

API return is never verification. Move/rename compare bounded SHA-256 identity evidence after independently confirming source absence; create-directory verifies an actual empty directory; deletion verifies path absence. File identity verification is capped at 8 MiB and reads in bounded chunks.

## Clipboard and keyboard verification

`agentx.capabilities.windows.input_verification` composes over the existing A5.06 execution capabilities rather than replacing their native ports. Construction requires a distinct execution port and verification port.

Clipboard read/write/clear verification uses a separate read-back seam. Payload content is compared in memory but never copied into verification detail. Keyboard/text verification requires an injected independent state observer returning typed evidence with a stable source and opaque UUID evidence reference. Native input acceptance alone cannot pass verification.

Independent verification evidence is observation only. It carries no permission, risk, gate, budget, task-success, procedure-activation or knowledge-promotion field and imports no authority owner.

## Trusted-Kernel integration

Safe local structural operations that the canonical ActionGate classifies as immediately allowable run through `CapabilityExecutionLoop` and can reach `SUCCEEDED` only after their independent verification passes.

The canonical gate deliberately returns `REQUIRE_CONFIRMATION` for R3/R4 external-effect/destructive actions. Existing human-approval contracts are evidence only and explicitly do not convert that result to `ALLOW`. This slice therefore does not add an approval bypass. Integration tests prove destructive deletion and Windows input are stopped before native execution by the current Trusted Kernel; the capability verification boundary remains ready for the future trusted confirmation-policy owner.

## Persistence, restart and concurrency

No second persistent store is introduced. Structural truth is current host filesystem state, and the capability objects hold no authoritative mutable state; reconstructed capability instances independently observe current state. Clipboard/keyboard verification is likewise current-state observation and intentionally stores no clipboard history or keystroke history. Persistence/restart is therefore N/A as a separate AgentX database requirement.

Filesystem races fail closed. Concurrent create of one directory yields at most one successful mutation, concurrent move of one source cannot duplicate its identity, destination collisions refuse replacement, and post-action tampering causes verification failure.
